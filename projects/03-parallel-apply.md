# 대용량 트랜잭션 병렬 반영 최적화

기술: C, Multithreading, WAL, Connection Pool, Red-Black Tree
소속: Tmax Tibero · 데이터 동기화 엔진팀

## 330자판 (293자)

```
[목표/배경]
단일 스레드로 트랜잭션을 반영하던 구조라 대용량 부하 시 병목이 컸고, 정합성을 지키며 처리량을 높여야 했습니다.
[역할·수행]
단일 스레드 반영을 스레드 풀 기반 트랜잭션 병렬 처리로 전환하고, 트랜잭션 간 의존성 검사를 위한 자료구조로 Red-Black Tree를 사용해 처리했습니다.
[성과·기여도]
부하 패턴에 따라 통상 2~3배, 부하 집중 시 최대 16배까지 처리량을 개선했고, 안정적인 메모리 예측성으로 여러 고객사에 배포했습니다. (개인 기여도 약 40% — 핵심 자료구조 RB tree 주도)
```

## 풀버전 (698자 · 포트폴리오/면접)

```
[목표/배경]
기존에는 단일 DB 커넥션으로 모든 트랜잭션을 직렬 반영해, 대용량 부하가 몰릴 때 반영이 병목이 됐습니다. 정합성(트랜잭션·DML 순서)을 지키면서 반영 처리량을 높이는 것이 과제였습니다.
[내 역할]
팀과 함께 최대 16스레드 커넥션 풀 기반 병렬 반영 구조를 설계했습니다. WAL 직렬화 모듈에서 커밋 트랜잭션과 내부 DML 간 의존성을 검사해, 병렬 반영 가능한 트랜잭션을 먼저 처리하도록 했습니다. 반영 단위(object/row) 판별 자료구조를 제가 주도해 해시 대신 rowid 정렬 기반 Red-Black Tree로 구현했습니다. rowid의 랜덤성 때문에 해시는 초기 소형 버킷에서 충돌이 폭증하고, 이를 피하려면 100M 이상 버킷이 필요한데 버킷당 메타데이터(포인터 포함)가 약 64B라 약 6.4GB를 이유 없이 상시 점유해야 했습니다. 사내 툴이면 몰라도, 고객에게 예측 가능한 메모리 사용량을 제시하고 이를 세일즈 포인트로 삼아야 하는 상용 제품에서는, 실제 데이터만큼만 자라고 O(N) 재해싱 스파이크도 없는 RB tree가 더 맞는 선택이었습니다. 더해 SQL Batch Update를 개선해 DB 반영 횟수를 줄였습니다.
[성과/기여]
병렬 반영을 안정화해, 부하 집중 시 최대 16배(스레드 수), 통상 2~3배 처리량을 개선했습니다. (타깃 DB 반영 지연·WAL 커밋 패턴에 따라 이득 폭은 달라짐)
```

## 핵심 포인트

- WAL 직렬화 모듈("constructor")이 커밋 트랜잭션·DML 간 dependency를 검사 → 독립 tx부터 병렬 반영.
- 병렬 반영 단위: object / row 두 모드 제공 (둘 다 개발, 내 주 기여는 자료구조).
- 해시 vs RB tree 결정 (내 개인 기여, 두 근거):
  1. 메모리: 해시는 rowid 랜덤성 → 100M+ 버킷 필요 → ×64B ≈ 6.4GB 상시 점유. 상용 제품 메모리 예측성에 치명적.
  2. 성능: 버킷 2배 확장 시 O(N) 재해싱 스파이크. RB tree는 예측 가능한 범위 내 제어.
- 커널 RB tree 코드 활용, rowid 기준 정렬.
